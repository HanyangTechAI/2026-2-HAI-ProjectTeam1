# Temporal 단독 제거 재실행 — 2K × H100, freeze 1.0.4

> 이 커밋은 보고서만 배포한다. 결과 JSON·JSONL·ZIP·그림과 실험 코드·설정은 별도로 보관하며, 아래 보관 경로와 재현 명령은 해당 로컬 산출물을 기준으로 한다. 핵심 수치와 해석은 본문 표에 포함했다.

2026-11-11, 수정한 `proposed/no_temporal`만 동일 시나리오 40개 × 두 반복으로 실행해 **80/80회 완료**했다. Temporal Resolution과 Version Chain Expansion은 OFF이며 Mandatory State, Constraint Preservation, Token-aware Packing은 ON이다. 실행 commit은 `f0abd2e9ec6e5a962fb3d834d2024a210d3a1c60`이며 실행 시작 시 작업 트리는 clean이었다. 다른 네 조건은 재실행하지 않았다.

Mandatory State는 설정에만 켜져 있는 것이 아니라, 80회 모두 최종 SelectionResult의 필수 State 목록에 2개 또는 3개 후보가 보존됐다. 시간 판별은 수행하지 않으므로 같은 key의 여러 버전도 보존한다. 수정 전 no_temporal과 비교했을 때 **80쌍 모두 성공 판정이 같았고 최종 선택 Memory ID 집합도 같았다**. 이번 입력에서는 Mandatory 승격을 복구해도 선택된 기억 집합과 최종 성공률이 달라지지 않았다. 이 관측만으로 Mandatory State의 일반적 기여가 없다고 해석하지 않는다.

실패 8회는 동일한 기본 과제 4개의 두 반복이다. 모두 `selection_failure`, `temporal_failure`, `stale_state_usage`가 함께 기록됐다. 조회 과제는 38/40회, 승인 과제는 34/40회 성공했다.

- `seed42_temporal_update_004_current`
- `seed42_approval_012_pending`
- `seed42_approval_013_granted`
- `seed43_approval_011_granted`

수정된 no_temporal의 성공률 95% CI는 [80.0%, 97.5%]다. 기존 Full과 같은 sample·repeat 80쌍을 비교한 성공률 차이(Full − 수정된 no_temporal)는 **+7.5pp, 95% CI [−2.5, +17.5]pp**다. 40개 기본 과제를 군집으로 묶은 bootstrap 2,000회(seed 42)를 사용했다. 이 CI는 Full과 재실행 조건만 입력한 별도 비교의 결과다. 기존 Full은 v1.0.3의 과거 실행이므로 동시 재실행 비교가 아니며, 차이의 CI도 0을 포함한다.

80회 모두 정상 종료했고 prompt audit은 모두 `verified`, 실제 입력 예산 초과는 0건(최대 1,823 token), 비용 회계는 모두 `complete`였다. 총 170회 LLM API 호출의 추정 비용은 **$0.164088**이다. 이 금액은 CountTokens와 기타 비용을 포함한 청구 총액이 아니다.

입력은 기존 `cell_e5534bba1746.json` 그대로다. 모델은 `gemini-3.1-flash-lite`, temperature 0, 출력 상한 2048 token, 입력 안전 여유 32 token, seed 42/43, 반복 2회를 유지했다. 기존 400회 결과를 덮어쓰거나 수정하지 않았다.
